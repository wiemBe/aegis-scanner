# Phase 1.5 — Controlled ZAP active reflected-XSS scanning

Status: **GO** (final, evidence-backed).

> Within the synthetic lab only, ZAP actively tests one reviewed reflected-XSS rule against one
> approved read-only GET operation by mutating one bounded query parameter, under a single-use
> operator lease that the runner verifies and consumes itself. The scanner's alert is a tool
> claim; an independent Aegis verifier owns the verdict.

The maximum claim this verdict supports is:

> GO for one controller-owned reflected-XSS active rule against one anonymous, read-only,
> resettable synthetic-lab endpoint under a runner-validated single-use lease, fixed network and
> traffic budgets, emergency stop, independently verified evidence and verified cleanup.

Nothing broader is claimed: no organization test-environment, staging or production readiness, no
broad active scanning, no broad OWASP coverage, no authenticated scanning, no arbitrary ZAP rules,
no AI-selected ZAP attacks, no browser execution, no application-wide safety.

Phase 1.3 is untouched: the passive profile, its 8-add-on image and its manifest are byte-identical
and remain the only ZAP capability with a live 5/5 acceptance.

## Responsibility boundary

- The operator requests the capability `zap_active_reflected_xss_v1` and, **separately**, authorizes
  a single-use activation lease by typing the exact phrase
  `ACTIVATE SYNTHETIC-LAB REFLECTED-XSS ACTIVE SCAN`. Enabling ZAP is not enough: without a live
  lease no active execution can start. The AI planner is not involved anywhere in this flow, and no
  model output can name a target, rule, payload, plan, job, option or URL.
- The controller selects the fixed profile `ZAP_LAB_ACTIVE_REFLECTED_XSS_V1`, resolves the target
  *reference* through its own inventory, builds the one-operation projection and constructs a typed
  `ZapActiveEngineJob`. Every policy rejection happens before the runner is contacted.
- The isolated active runner re-derives the projection from its own copy of the source, revalidates
  the target, profile, projection digest, allowlist digest, query parameter and budgets, generates
  the fixed Automation Framework plan, byte-compares it with a freshly generated one, and only then
  starts the pinned ZAP behind the scope guard.
- The lease is runner-enforced: the controller signs an HMAC-SHA-256 `AZL1` lease whose claims bind
  the capability, profile, target, origin, digests, audience, budget and a single-use nonce. The
  runner's root-owned admission component verifies it independently, admits exactly one ARMED
  lease, consumes it atomically when execution begins (exactly one winner under concurrency),
  revokes it on stop/failure/completion, keeps the nonce memory across restarts and binds the scope
  guard to the same lease — a valid signature alone never executes anything.
- The active-rule manifest review is operator-countersigned (record
  `countersign-zap-active-reflected-xss-v1`): the manifest digest, the admitted rule, the
  ascanrules/oast/database digests, the profile, the capability and the environment are frozen, and
  `build_zap_active_job` refuses any drift before a projection exists.
- **Payloads are ZAP's own**, generated by rule 40012 inside the admitted policy. The operator, the
  model and the RPC caller can never supply an attack string.
- ZAP alerts enter as `TOOL_REPORTED`. Only `aegis.zap_active_verifier` — which issues its own fresh
  requests with a per-execution random marker — can produce `VERIFIED` or a patched `PASS`.

### Why `oast` and `database` are in the image

`ascanrules` hard-depends on `oast`, and `oast` hard-depends on `database`. Both are otherwise
forbidden add-ons. They are admitted **only** as `FORCED_DEPENDENCY_NEUTRALISED` (the same treatment
as `callhome`) and recorded as such in `neutralised_dependency_ids`: rule 40012 uses neither, no OAST
job is expressible in the profile, `oast` is in `prohibited_jobs`, `oastCallbacks` is in
`prohibited_features`, and the runner container has no network route except the scope guard, so an
OAST callback has nowhere to go. The operator approved this explicitly on 2026-09-20.
`ascanrules-release-78`, also present in the base image, is deleted at build time.

## The narrow attack surface

The projection produces a new OpenAPI 3.0.3 document containing exactly one `GET`
`/lab/zap-active/{variant}/search` operation with exactly one bounded query parameter `q`
(`maxLength: 32`). `addQueryParam` is false and `scanHeadersAllRequests` is false, so ZAP may mutate
`q` and nothing else — no second parameter, no header, no path, no method, no body.

The synthetic lab routes are stateless, hold no credential or business data, and are excluded from
the application's own OpenAPI. The two variants differ **only** in output encoding: the vulnerable
route reflects `q` raw into an executable HTML element context, the patched route reflects the
identical value through `html.escape(..., quote=True)`. `reset` is a deterministic no-op because
there is no state to reset.

## Evidence and redaction

ZAP's `attack` field (the payload it sent) and `evidence` field (what it saw reflected) are **never
stored or propagated**. The parser reduces each to a length and a SHA-256, plus a coarse structural
attack *class* (`SCRIPT_ELEMENT`, `ATTRIBUTE_BREAKOUT`, `EVENT_HANDLER`, `JS_URI`,
`MARKUP_INJECTION`, `OTHER`, `NONE`) so identical alerts correlate deterministically. Scanner prose
(`desc`, `solution`, `otherinfo`, `reference`, `riskdesc`, `tags`) is counted as stripped and never
propagated. ZAP's risk and confidence survive only as untrusted `claimed_*` labels and never set
Aegis severity or confidence.

### The verifier

`aegis.zap_active_verifier` trusts nothing ZAP produced. The controller mints a fresh random marker
per execution and the verifier issues two of its own read-only GETs:

- `BASE_CONTROL` — `?q=benign-<marker>` must return `200 text/html` carrying the synthetic
  variant marker (proves reachability and exact routing);
- `XSS_PROBE` — `?q=<script><marker></script>`, classified deterministically as `RAW_EXECUTABLE`,
  `ENTITY_ENCODED`, `AMBIGUOUS` or `ABSENT`.

`CONFIRMED` requires the raw executable element bearing the fresh marker; `PASS` requires the
cleanly entity-encoded form; anything else is `INSUFFICIENT`. **No browser executes the marker, so
the verifier never claims execution** — it proves that controller-controlled input reaches an
executable HTML context without contextual output encoding, which is the defining condition of the
reflected-XSS class. Only body-free facts and digests are persisted.

Lifecycle: `TOOL_REPORTED` → `AEGIS_CORRELATED` → `VERIFIED` (vulnerable) or `REJECTED` (patched
PASS) or `REVIEW_REQUIRED` (insufficient). Zero alerts is never by itself a PASS: a PASS additionally
requires complete coverage, zero guard blocks, a drained passive queue and a verifier verdict.

Defects found and fixed during the matrix (each re-run to green): the admission dependency lock
was generated for the cp311 interpreter but the admission image used Python 3.12 (pip
`--require-hashes` correctly failed closed; the admission base is now pinned Python 3.11 so both
sides run the same verified wheel set); the runner image lacked the shared admission contract
shapes (moved into `aegis_zap_active.contracts`, re-exported by `zap_active_admission.contracts`);
the controller armed the lease twice (once at activation, once inside the adapter's `run`) so the
second arm collided with the already-armed registry entry (arming is now exclusively the
activation ceremony's job); the admission status response exceeded the 8 KiB bounded-client
ceiling once the registry held a full history (ceiling raised to 16 KiB with a regression test);
the emergency-stop kill raced the run loop's disarm (stop order is now revoke → guard disarm →
kill → STOPPED under a stop lock, and the guard keeps the revocation marker through the disarm);
the runner's stop classification reported `NONZERO_EXIT` for a SIGKILLed engine (now
`KILLED_BY_GUARD`).

### Not executed: a real closed test environment

No scan has been run against any non-synthetic target. `ZAP_TEST_ENV_ACTIVE_V1`
(`aegis.zap_active_test_env`) is implemented but **inert**: this repository ships no test-environment
target, origin or OpenAPI document. To enable one, the operator must register
`TARGET_ORIGIN` (the exact registered origin), `OPENAPI_FILE` (an approved **local** document, never
a URL) and optionally `ALLOWED_PATH_PREFIX`. No credential is requested, required or accepted on this
path. `preflight()` must then return empty: resolved origin equals the registered origin,
classification is `CONTROLLED_TEST_ENV`, the guard is armed, the kill switch is verified, the request
budget is installed, no route bypasses the guard, no secret is present in ZAP or the guard, and the
rate (≤ 2/s), request ceiling (≤ 500), wall clock (≤ 10 min), rule subset (40012 only) and read-only
method set are within bounds. This GO does not claim any closed-test-environment readiness.
